방장은 방을 운영하는 역할이고, 발표자는 현재 말하거나 화면을 공유하는 역할입니다. 일반 참여자도 방장이 발표자로 지정하면 발표할 수 있습니다. 발표자로 지정하는 것과 방장 권한을 넘기는 것은 다른 동작입니다.

기본값과 현재 제공 범위

  • 입장 설정에서 마이크·스피커는 기본 꺼짐이며 카메라도 기본 꺼짐입니다. 직전 회의에서 사용했어도 새 입장 시 다시 확인합니다.
  • 서버 주소와 표시 이름만 같은 브라우저에 저장할 수 있습니다. 장치 사용 여부와 참가 인증 토큰은 영구 저장하지 않습니다.
  • 기본 한 방 최대 인원은 8명입니다. 관리자가 설정을 바꿀 수 있으나, 실제 수용 인원은 서버와 네트워크 성능을 검증해 정해야 합니다.
  • 자동 회의록은 한국어 음성 인식 결과를 발언자별로 묶고 결정·실행 후보를 추출합니다. 생성형 AI 요약이나 사실 확인 기능은 포함하지 않습니다.
  • 파일은 발표자가 열어 둔 창을 공유하는 방식입니다. 파일 업로드, 공동 문서 편집, 시스템 소리 공유는 제공하지 않습니다.
  • 영상·음성 녹화 파일은 저장하지 않습니다. 회의록 텍스트는 서버 DB에 저장합니다.
  • 진행 중인 방, 발표권, 화이트보드는 서버 메모리에 있습니다. 서버가 재시작되면 이전 방은 복원되지 않습니다. 회의록 DB는 별도로 보존됩니다.
  • 대기실, 참가 승인, 강제 퇴장, 전체 참가자 강제 종료, 수동 방장 양도, 사용자 계정 인증은 현재 화면에 없습니다.

빠른 시작

일반 참여자는 초대 링크 열기 → 이름 확인(서버 주소·방 접속 ID 자동 입력) → 회의 참여하기 → 스피커 켜기 → 필요시 손들기와 마이크 켜기 순서로 사용합니다. 서버 주소와 접속 ID를 직접 입력하는 방법도 가능합니다.

방장은 주소 열기 → 새 회의 만들기 → 방식과 회의록 옵션 선택 → 새 회의 시작하기 → 참석자 탭에서 초대 링크 복사 → 발표 지정 → 회의록 저장 순서로 진행합니다.

서버 관리자는 설치 환경 확인 → 서버 파일 배치 → Docker와 Compose 준비 → 도메인·네트워크 설정 → 컨테이너 실행 → 다중 PC 시험 → 자동 시작 확인 순서로 구축합니다.

초대 링크로 빠르게 참여하기

  1. 방장이 보낸 초대 링크를 Chrome 또는 Edge에서 엽니다. 예: https://meet.example.com/#room=4AB891762964.
  2. 초대 링크로 접속했습니다 안내와 자동 입력된 서버 주소·방 접속 ID를 확인합니다. 이전에 저장한 서버 주소가 있어도 초대 링크의 서버를 사용합니다.
  3. 내 이름을 입력하거나 저장된 이름을 확인합니다.
  4. 마이크·스피커·카메라를 사용할지 선택합니다. 기본값은 모두 꺼짐이며 링크를 여는 것만으로 입장하거나 장치를 켜지 않습니다.
  5. 회의 참여하기를 누릅니다. 입장 후 상대방 소리를 들으려면 스피커를 켜세요.

링크의 ID가 올바르지 않다는 안내가 나오면 방장에게 전체 링크를 다시 받으세요. 종료된 방은 기존 링크로 들어갈 수 없으므로 새 방의 링크를 받아야 합니다. 링크 없이 서버 주소와 접속 ID를 받은 경우에는 아래 절차를 따릅니다.

1 접속 전에 준비하기

  1. 방장에게 중계 서버 주소와 방 접속 ID를 받습니다.
  2. PC에서 Chrome 또는 Edge를 엽니다. 화면 공유는 데스크톱 브라우저를 기준으로 설명합니다.
  3. 헤드셋 또는 이어폰을 연결합니다. 마이크가 있는지 확인합니다.
  4. 다른 화상회의 앱이 카메라·마이크를 사용 중이면 정리합니다.

브라우저의 장치 권한과 프로그램의 장치 버튼은 별개입니다. 브라우저에서 마이크 사용을 허용했더라도 프로그램의 마이크가 꺼져 있으면 음성이 전달되지 않습니다.

4.3 회의 모드에서 말하기

  1. 하단의 손들기를 누릅니다.
  2. 버튼이 손 내리기로 바뀌고, 방장의 참석자 목록에 발언 요청이 표시됩니다.
  3. 방장이 본인을 발표 지정할 때까지 기다립니다.
  4. 본인이 발표자라는 안내를 확인합니다.
  5. 마이크가 꺼져 있으면 직접 켭니다. 발표권을 받아도 마이크가 자동으로 켜지지는 않습니다.
  6. 발표권이 다른 사람에게 넘어가면 본인의 음성이 서버에서 차단되고, 켜 둔 마이크는 대기 상태가 됩니다.

발표권은 한 명에게만 지정됩니다. 자동 회의록 옵션이 꺼져 있어도 회의 모드는 한 사람씩 발표합니다. 자동 순번 배정 기능은 없고 방장이 발표 순서를 정합니다.

화면 배치는 본인의 화면에만 적용됩니다. 내가 화이트보드로 바꿨다고 다른 사람도 자동으로 바뀌지 않습니다. 발표자가 화면을 공유하면 각자 발표자 탭을 선택해 크게 보세요. 전체 화면은 Esc로 나올 수 있습니다.

카메라가 꺼진 참석자는 영상 대신 이름의 첫 글자가 표시됩니다. 화면을 어떤 탭으로 바꾸더라도 스피커를 켜 두었다면 참석자의 음성은 계속 들립니다.

6 발표자로 지정됐을 때 화면과 파일 공유하기

6.1 열린 파일 함께 보기

  1. 발표할 PDF, 문서, 스프레드시트, 슬라이드 또는 이미지를 PC에서 먼저 엽니다.
  2. 방장에게 발표자로 지정해 달라고 요청합니다.
  3. 하단 화면·파일 공유를 누릅니다.
  4. 브라우저 선택 창에서 공유할 창, 탭 또는 전체 화면을 선택합니다.
  5. 공유를 시작하고 참석자에게 발표자 탭을 선택해 달라고 안내합니다.
  6. 파일을 넘기거나 스크롤하면서 설명합니다.
  7. 설명이 끝나면 공유 중지 또는 브라우저의 공유 중지 버튼을 누릅니다.

공유 중에는 본인의 카메라 영상 자리에 공유 화면이 전송됩니다. 카메라와 화면을 동시에 두 개의 영상으로 전송하지 않습니다. 공유를 멈추면 켜 둔 카메라로 돌아가고, 카메라가 꺼져 있으면 아바타로 돌아갑니다.

이 기능은 파일을 서버에 업로드하지 않습니다. 다른 참석자가 파일을 다운로드하거나 함께 수정하는 기능은 없습니다. 동영상이나 음악의 시스템 소리는 공유하지 않으며 발표자의 마이크로 설명합니다. 공유할 창에 표시되는 내용은 참석자가 볼 수 있으니 공유 대상을 선택할 때 확인하세요.

6.2 화이트보드 사용하기

  1. 화이트보드 탭을 선택합니다.
  2. 본인이 현재 발표자인지 확인합니다.
  3. 펜 색과 두께를 선택합니다.
  4. 마우스를 누른 채 움직이거나 터치로 그립니다.
  5. 참석자는 자신의 화이트보드 탭에서 내용을 봅니다.

지우기는 보드 전체를 지웁니다. 실행 취소나 부분 지우개는 없습니다. 지운 내용은 되돌릴 수 없으므로 함께 보고 있는 사람이 내용을 확인했는지 먼저 확인하세요. 화이트보드 저장·내보내기 버튼도 없으므로 필요한 그림은 회의 중 OS 화면 캡처로 보관합니다.

늦게 입장한 사람도 현재 방의 그림을 받습니다. 그러나 마지막 사람이 나가거나 서버가 재시작되면 보드는 사라집니다.

7 회의록 보기와 저장하기

  1. 오른쪽 회의록 탭을 누릅니다.
  2. 음성 인식 기록 중 또는 자동 기록 꺼짐 표시를 확인합니다.
  3. 자동 기록 중이면 발표자의 발언이 문장 단위로 잠시 뒤 표시됩니다.
  4. 방장이 추가한 확정 결정, 실행 항목, 추가 메모를 확인합니다.
  5. 상단 회의록 저장을 누릅니다.
  6. 브라우저 다운로드 폴더에서 회의록-접속ID.md 파일을 확인합니다.

일반 참여자도 자기 방의 회의록을 다운로드할 수 있습니다. 일반 참여자는 기록을 추가·수정하거나 자동 기록 옵션을 바꿀 수 없습니다. 전사 오류가 있으면 방장에게 정정 메모를 남겨 달라고 요청하세요.

화면에는 최근 200개 기록이 표시되며 다운로드 파일에는 그 시점까지 DB에 저장된 전체 기록이 들어갑니다. 마지막 발언은 인식 완료까지 시간이 걸릴 수 있으므로 발언을 마친 뒤 기록이 표시됐는지 확인하고 저장하세요. 저장 파일의 시간은 UTC이며 한국 시간은 UTC보다 9시간 빠릅니다. 화면의 시간은 브라우저 현지 시간으로 표시됩니다.

8 나가기와 다시 입장하기

  1. 필요한 회의록을 먼저 저장합니다.
  2. 하단 나가기를 누릅니다.
  3. 접속 설정 화면으로 돌아왔는지 확인합니다.

같은 방에 다른 사람이 남아 있다면 동일한 접속 ID로 다시 들어갈 수 있습니다. 새로고침이나 브라우저 종료도 연결을 끊을 수 있으며, 자동 재입장 기능은 없습니다. 재입장 시 마이크·스피커·카메라는 다시 확인하세요.

마지막 사람이 나가면 방이 종료됩니다. 종료된 접속 ID는 다시 사용할 수 없으며 방장이 새 방을 만들어야 합니다. 혼자 있는 방에서 새로고침해도 기존 방이 종료될 수 있습니다.

2 새 방 만들기

  1. 서버 관리자가 알려준 HTTPS 주소를 Chrome 또는 Edge에서 엽니다.
  2. 중계 서버 주소를 확인하고 연결 확인을 누릅니다.
  3. 내 이름을 입력합니다. 예: 김민수 팀장.
  4. 마이크·스피커·카메라 사용 여부를 정합니다. 기본값은 모두 꺼짐입니다.
  5. 새 회의 만들기 탭을 선택합니다.
  6. 회의 이름을 입력합니다. 예: 제품팀 주간 회의. 최대 80자입니다.
  7. 회의 방식에서 FREE Talk 또는 회의 모드를 선택합니다.
  8. 자동 기록이 필요하면 회의 모드에서 음성 인식으로 자동 회의록 작성을 선택합니다.
  9. 새 회의 시작하기를 누릅니다.
  10. 회의 화면에서 본인의 방장 표시, 회의 이름, 접속 ID를 확인합니다.

방을 만들면 방장 자신이 최초 발표자로 지정됩니다. 마이크가 꺼져 있다면 발표자여도 음성이 나오지 않으므로 직접 켜야 합니다.

자동 회의록 옵션이 비활성화되어 있으면 FREE Talk가 선택됐는지, 서버 연결 확인이 성공했는지, 안내에 한국어 모델 미설치 또는 로딩 실패가 표시되는지 확인하세요. 모델 설치 문제는 서버 관리자가 해결해야 합니다.

3 초대 링크·접속 ID 공유와 참석자 확인

  1. 방을 만든 뒤 오른쪽 참석자 탭에서 참여자 초대 링크를 확인합니다. 방장에게 표시되는 메뉴입니다.
  2. 초대 링크 복사를 누르고 이메일·메신저 등 원하는 수단에 붙여 넣습니다.
  3. 참석자에게 링크를 열고 이름과 장치 설정을 확인한 뒤 회의 참여하기를 누르도록 안내합니다. 서버 주소와 방 접속 ID는 자동 입력됩니다.
  4. 오른쪽 참석자 탭에서 이름과 인원수를 확인합니다.

공유 예:

text
회의: 제품팀 주간 회의
초대 링크: https://meet.example.com/#room=4AB891762964

링크를 열고 이름을 입력한 뒤 회의 참여하기를 눌러 주세요.
마이크와 스피커는 기본 꺼짐입니다.
입장 후 스피커를 켜고, 발언할 때는 손들기를 눌러 주세요.

방 접속 ID는 서버가 자동으로 생성합니다. 방장이 직접 지정하거나 기존 방의 ID를 바꾸는 기능은 없습니다. 코드 자체가 입장 수단이므로 참석할 사람에게 공유하세요. 현재는 방장 승인 대기실이나 별도 입장 비밀번호가 없습니다.

클립보드 복사가 실패하면 링크 입력란이 선택됩니다. Ctrl+C 또는 모바일의 길게 누르기로 직접 복사하세요. 기존 상단 접속 ID 복사로 서버 주소와 접속 ID를 전달하는 방법도 사용할 수 있습니다.

초대 링크에는 방 접속 ID만 포함되고 방장 인증 토큰은 포함되지 않습니다. 링크를 받은 사람은 일반 참여자로 입장합니다. 다른 사람에게 전달된 링크로도 입장할 수 있으므로 참석할 사람에게 공유하세요. 방장이 먼저 나가면 다음 방장에게 초대 메뉴가 표시됩니다.

마지막 참석자가 나가거나 서버가 재시작되어 방이 종료되면 기존 링크로 재입장할 수 없습니다. 새 방을 만들고 새 링크를 공유하세요. localhost 주소는 다른 PC용 초대 주소로 사용할 수 없습니다. 외부 초대는 참석자가 접속할 수 있는 HTTPS 서버 주소로 접속해 방을 만든 뒤 링크를 복사합니다.

4 회의 시작 점검

  1. 전원에게 스피커를 켜 달라고 안내합니다.
  2. 본인이 발표자인지 확인하고 마이크를 켭니다.
  3. 짧게 말한 뒤 참석자가 듣는지 확인합니다.
  4. 참석자 한 명을 발표자로 지정해 반대 방향 음성도 확인합니다.
  5. 화면 공유와 화이트보드를 쓸 예정이면 각 기능을 한 번 확인합니다.
  6. 자동 회의록을 사용하는 회의임을 참석자에게 알리고 기록 상태를 확인합니다.

서버 주소가 열리고 방에 입장할 수 있다는 것만으로 영상·음성이 연결된 것은 아닙니다. 다른 네트워크의 참석자가 있다면 그 참석자의 영상·음성도 확인하세요.

5 발표 순서 운영하기

5.1 일반 참여자에게 발표권 주기

  1. 오른쪽 참석자 탭을 엽니다.
  2. 발언을 요청한 사람의 이름 옆에 발언 요청 표시가 있는지 확인합니다.
  3. 해당 사람의 발표 지정 버튼을 누릅니다.
  4. 해당 사람이 발표자로 표시되는지 확인합니다.
  5. 그 사람의 마이크가 꺼져 있다면 직접 켜 달라고 안내합니다.

발표자로 지정된 사람의 손들기 표시는 해제됩니다. 이전 발표자의 음성은 회의 모드에서 차단됩니다. 이전 발표자가 화면을 공유 중이었다면 공유도 중지되므로 발표권을 넘기기 전에 설명이 끝났는지 확인하세요.

5.2 방장 자신이 다시 발표하기

  1. 참석자 목록에서 본인 이름을 찾습니다.
  2. 본인 옆 발표 지정을 누릅니다.
  3. 본인의 마이크를 켜거나 켜진 상태인지 확인합니다.

방장이란 이유만으로 다른 발표자와 동시에 말할 수 있는 것은 아닙니다. 회의 모드에서는 방장에게도 동일한 단일 발표 규칙이 적용됩니다.

5.3 FREE Talk 진행하기

FREE Talk에서는 모두 마이크를 켜면 동시에 말할 수 있습니다. 이때 발표자 지정은 주로 공유 화면과 화이트보드 조작자를 정하기 위해 사용합니다. 방장이 다른 사람의 마이크를 강제로 켜거나 끄는 기능은 없습니다.

6 자동 회의록 운영하기

6.1 진행 중 켜기와 끄기

  1. 오른쪽 회의록 탭을 선택합니다.
  2. 회의 모드에서 켜기를 누릅니다.
  3. 음성 인식 기록 중 표시를 확인합니다.
  4. 현재 발표자가 마이크를 켜고 말합니다.
  5. 발언자 이름과 전사 내용이 표시되는지 확인합니다.
  6. 기록을 중지할 때 끄기를 누릅니다.

옵션을 켠 뒤의 음성만 인식합니다. 꺼져 있던 구간을 나중에 복구해 기록하지 않습니다. 옵션을 끄거나 발표권이 바뀌는 순간 직전 발언의 마지막 인식 결과가 잠시 뒤 도착할 수 있습니다. 자동 기록을 끄더라도 이미 저장된 기록은 지워지지 않습니다.

6.2 정확도를 높이는 진행 방법

  • 한 번에 한 사람이 말하고, 말이 끝날 때 짧게 쉬어 줍니다.
  • 마이크를 입 가까이에 두고 불필요한 주변 소음을 줄입니다.
  • 사람 이름, 제품명, 숫자, 날짜, 약어는 전사 결과를 확인합니다.
  • 중요한 결정은 방장이 다시 확인하고 별도의 확정 기록으로 남깁니다.

화면의 자동 전사는 검토할 원문입니다. 현재 버전은 전사를 문맥에 따라 완전히 교정하거나 고급 요약하는 기능이 아닙니다.

6.3 확정 결정과 실행 항목 남기기

  1. 회의록 탭의 방장 기록 추가로 이동합니다.
  2. 종류를 선택합니다.
  3. 내용을 작성하고 기록 추가를 누릅니다. 한 번에 최대 2,000자입니다.
종류기록 예
추가 메모전사 정정: 제품 이름은 모아입니다.

기존 기록의 편집·삭제 버튼은 없습니다. 잘못 입력했으면 추가 메모로 정정 내용을 남기세요. 자동 추출된 결정·실행 후보를 확인했더라도 확정 내용으로 남기려면 방장이 해당 종류로 새로 기록해야 합니다.

6.4 회의록 저장 파일의 구성

회의록 저장을 누르면 다음 순서로 정리된 Markdown 파일을 내려받습니다.

  1. 회의 제목, 시작·내보내기 시각
  2. 기록에 등장한 발언자
  3. 발언자별 주요 논의 원문
  4. 방장이 입력한 확정 결정
  5. 방장이 입력한 실행 항목
  6. 추가 메모
  7. 키워드로 자동 분류한 결정·실행 후보
  8. 시간순 원문

참석 발언자는 전체 출석부가 아닙니다. 기록에 등장한 사람을 기준으로 하므로 조용히 듣기만 한 사람은 빠질 수 있습니다. 부정문도 키워드 후보로 잡힐 수 있어 자동 후보는 미확정 상태로 분리됩니다.

7 발표 자료와 화이트보드 진행

방장도 현재 발표자여야 화면·파일 공유와 화이트보드 그리기를 사용할 수 있습니다. 파일을 먼저 연 뒤 공유할 창을 선택하고 참석자에게 발표자 화면으로 바꿔 달라고 안내하세요.

화이트보드를 쓸 때는 참석자에게 각자 화이트보드 탭을 선택하도록 안내합니다. 지우기는 전체 내용을 삭제하며 되돌리기 기능은 없습니다. 기록이 필요한 그림은 회의가 끝나기 전에 화면 캡처로 보관하세요.

8 회의 종료와 방장 퇴장

정상 종료 순서

  1. 마지막 발표자의 발언을 마칩니다.
  2. 마지막 전사 내용이 표시되는지 확인합니다.
  3. 확정 결정과 실행 항목의 담당자·기한을 확인합니다.
  4. 회의록 저장으로 최종 파일을 내려받습니다.
  5. 필요한 참석자도 회의록을 저장하도록 안내합니다.
  6. 참석자들에게 나가 달라고 안내합니다.
  7. 방장은 마지막으로 나가기를 누릅니다.

방장이 나가기만 해서는 전체 회의가 끝나지 않습니다. 다른 참석자가 남아 있으면 그중 한 사람에게 방장 권한이 자동으로 이전됩니다. 현재는 전체 방 종료 버튼이 없습니다.

방장이 먼저 나가거나 연결이 끊긴 경우

  • 서버는 남아 있는 접속자 중 먼저 들어온 사람을 우선하여 방장으로 정합니다.
  • 원하는 사람을 직접 방장으로 지정하는 UI는 없습니다. 발표자 지정은 방장 이전 기능이 아닙니다.
  • 기존 방장이 다시 입장해도 이전 권한이 자동 복구되지 않습니다.
  • 모든 사람이 나가면 방은 종료되고 기존 접속 ID로 다시 들어갈 수 없습니다.
  • 새로고침도 연결 종료로 처리될 수 있으므로 진행 중인 방장 화면을 불필요하게 새로고침하지 마세요.

1.1 Ubuntu 20.04의 지원 상태

아래 20.04 절차는 기존 서버를 유지해야 하는 환경에서 남아 있는 focal 패키지를 사용하는 설치 경로입니다. 현재 Docker focal 패키지 저장소는 확인되지만, 저장소가 남아 있다는 사실이 최신 버전 지원이나 보안 유지보수를 보장하지는 않습니다. 이미 관리 중인 Docker가 정상 설치돼 있으면 재설치하지 말고 버전과 Compose 동작을 확인한 뒤 3장부터 진행하세요.

2 Docker와 Compose 준비

아래 명령은 Ubuntu 서버 터미널에서 실행합니다. Windows PowerShell용 명령이 아닙니다.

2.1 기존 환경 확인

bash
cat /etc/os-release
uname -m
df -h
free -h
docker --version
sudo docker version
sudo docker compose version

명령이 없다는 메시지는 해당 도구가 미설치된 경우입니다. docker compose version이 정상 표시되면 Compose 설치를 반복하지 않습니다. 이 프로젝트는 공백이 있는 docker compose 명령을 사용합니다. 옛 docker-compose v1만 있는 환경은 Compose 플러그인이 필요합니다.

기존 패키지 확인:

bash
dpkg -l docker.io docker-ce docker-ce-cli containerd containerd.io runc

서로 다른 공급자의 Docker·containerd 패키지를 무작정 섞어 설치하지 마세요. 기존 컨테이너가 있는 서버에서는 패키지 제거가 다른 서비스에 영향을 줄 수 있습니다. 충돌 패키지 정리는 기존 운영 담당자와 상태를 확인한 뒤 수행합니다.

2.2 Docker 미설치 Ubuntu 20.04에 focal 저장소 등록

기존 Docker가 없는 서버에서 진행합니다. /etc/os-release의 코드명이 focal인지 먼저 확인하세요. 다른 Ubuntu 버전에 focal 저장소를 등록하지 않습니다.

bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl python3 rsync nano
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
MEETING_ARCH=$(dpkg --print-architecture)
printf 'deb [arch=%s signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu focal stable\n' "$MEETING_ARCH" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
apt-cache policy docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

각 패키지의 Candidate가 실제 버전인지 확인합니다. (none)이거나 저장소 서명 오류가 나면 다음 설치를 진행하지 말고 패키지 공급 경로를 확인하세요. 다른 Ubuntu 코드명의 패키지를 억지로 설치하지 않습니다. 패키지가 제공되는 환경에서는 다음을 실행합니다.

bash
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker.service
sudo systemctl enable --now containerd.service
sudo docker version
sudo docker compose version
sudo docker run --rm hello-world

이 안내는 Docker 명령 앞에 sudo를 붙입니다. 사용자를 Docker 그룹에 추가하는 별도 절차는 필수가 아닙니다. 설치 방식의 기본 구조는 Docker apt 설치 안내를 따르며, focal 사용 조건은 위 1.1절을 적용합니다.

3 서버 파일 배치

이하 명령은 새 설치 위치를 /opt/moa, Compose 프로젝트 이름을 moa로 통일합니다. 기존 배포에 데이터가 있다면 기존 프로젝트 이름을 유지해야 합니다. 프로젝트 이름이 달라지면 새 DB 볼륨이 만들어질 수 있습니다.

3.1 Windows에서 파일 전달

Windows 탐색기와 SFTP 도구로 화상회의/RelayServer 폴더를 Ubuntu 계정의 홈 디렉토리에 올려도 됩니다. Windows OpenSSH가 있다면 PowerShell에서 다음처럼 전송할 수 있습니다.

powershell
scp -r "C:\Users\063\Downloads\교육_1014\화상회의\중계서버" admin@SERVER_IP:/home/admin/

admin, SERVER_IP, /home/admin/을 실제 접속 계정과 주소로 바꿉니다. 상위 화상회의/.venv는 Windows용이므로 Ubuntu에 복사하지 않습니다. 샘플 시험 데이터가 들어 있는 data, 테스트 캡처인 test-results, Python 캐시도 신규 운영 데이터로 사용하지 않습니다.

3.2 Ubuntu의 배포 위치 준비

다음은 현재 Ubuntu 로그인 계정이 배포 파일을 관리하는 새 설치 예입니다.

bash
sudo install -d -m 0755 /opt/moa
sudo chown "$(id -un):$(id -gn)" /opt/moa
rsync -a --exclude '.venv' --exclude '__pycache__' --exclude '.pytest_cache' --exclude 'data' --exclude 'test-results' "$HOME/RelayServer/" /opt/moa/
cd /opt/moa
ls server.py Dockerfile compose.yaml .env.example

rsync의 원본 끝 /는 폴더 자체가 아니라 그 안의 내용을 복사한다는 뜻입니다. 서버에 직접 모델을 내려받으려면 전송 시 models도 제외할 수 있습니다.

4 설정 파일 작성

4.1 새 설치의 환경 파일 만들기

bash
cd /opt/moa
cp -n .env.example .env
nano .env

cp -n은 이미 있는 .env를 덮어쓰지 않습니다. nano에서 수정 후 Ctrl+O, Enter로 저장하고 Ctrl+X로 나옵니다.

dotenv
DOMAIN=meet.example.com
DB_PATH=/app/data/meetings.db
VOSK_MODEL_PATH=/app/models/vosk-model-small-ko-0.22
MAX_PARTICIPANTS=8
MAX_ROOMS=30
ALLOWED_ORIGINS=
ICE_SERVERS_JSON=[]

DOMAIN에는 https:// 없이 실제 도메인만 넣습니다. DB_PATH와 VOSK_MODEL_PATH는 컨테이너 안의 경로이므로 위 값을 유지합니다. 모든 참여자가 같은 서버가 제공한 화면을 쓰면 ALLOWED_ORIGINS는 비워 둡니다.

ICE_SERVERS_JSON=[]는 추가 STUN/TURN 서버를 쓰지 않는 초기값입니다. 같은 LAN에서 서버의 미디어 UDP에 직접 도달할 수 있는 시험에 사용할 수 있습니다. 인터넷·공유기·회사망 환경은 6장의 TURN 설정을 함께 검토하세요.

bash
chmod 600 .env

공식 모델은 약 82MB 다운로드이며 압축 해제 공간이 추가로 필요합니다. 이미 정상 모델 파일이 있으면 다운로드 스크립트는 다시 받지 않습니다. 모델 설치 후 실행 중인 서버는 재시작해야 모델을 읽습니다. 모델이 없어도 회의와 수동 메모는 가능하지만 자동 회의록은 비활성화됩니다. 모델 출처는 Vosk 모델 목록입니다.

5 HTTPS와 방화벽

5.1 DNS와 웹 포트

도메인의 DNS가 실제 서버 공인 IP를 가리키도록 설정합니다. 공유기 뒤 서버라면 TCP 80/443을 서버 내부 IP로 전달합니다. 기존 Apache·Nginx·다른 Caddy가 이미 80/443을 사용하고 있는지 확인하세요.

bash
sudo ss -lntp
getent ahosts meet.example.com

Caddy가 공인 인증서를 발급·갱신하려면 도메인과 검증 경로가 실제로 도달 가능해야 합니다. 이 예제는 TCP 80/443을 개방하는 구성이며, 단순 사설 IP 입력만으로 공인 도메인 인증서가 발급되지는 않습니다. Caddy 자동 HTTPS 안내.

Python 미디어 포트는 현재 앱에서 별도 범위로 고정하지 않습니다. 실제 서버 범위를 읽습니다.

bash
cat /proc/sys/net/ipv4/ip_local_port_range

예를 들어 출력이 32768 60999라면 해당 범위의 UDP 경로를 방화벽·보안 그룹·필요한 NAT 규칙에서 검토합니다. 이 숫자는 예시이며 다른 값을 출력하는 서버에 그대로 적용하지 않습니다.

UFW를 이미 사용하는 서버의 규칙 추가 예:

bash
sudo ufw status verbose
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
# 실제 범위가 32768~60999일 때만 적용하는 예
sudo ufw allow 32768:60999/udp
# TURN을 사용할 때 추가
sudo ufw allow 3478/tcp
sudo ufw allow 3478/udp
sudo ufw allow 49160:49260/udp

UFW가 비활성이면 위 규칙만 추가한다고 방화벽이 활성화되지는 않습니다. 원격 작업 중 ufw enable을 실행하기 전에는 실제 SSH 포트 허용 여부부터 확인하세요. 회사망·클라우드 보안 그룹·공유기 포트 전달은 UFW와 별도로 설정해야 합니다. 직접 접속 대역을 제한할 수 있으면 전체 인터넷 대신 그 대역에 한정합니다.

6 TURN 설정

HTTPS는 접속되지만 서로 다른 네트워크에서 영상·음성이 안 되는 경우 NAT 또는 UDP 경로 문제가 흔합니다. TURN은 이런 환경의 미디어 중계를 위한 별도 서비스입니다. 앱의 Python 중계 서버와 역할이 다릅니다.

6.1 coturn 설정 파일 수정

bash
cd /opt/moa
openssl rand -hex 24
nano deploy/turnserver.conf

위 명령이 출력한 임의 문자열을 TURN 비밀번호로 사용합니다. 예제 설정에서 최소 다음 값을 바꿉니다.

ini
realm=meet.example.com
user=meeting:생성한_영문숫자_비밀번호

서버가 NAT 뒤에 있다면 다음 형식으로 외부/내부 IP를 지정합니다.

ini
external-ip=203.0.113.10/192.168.0.10

위 IP는 설명용입니다. 실제 공인 IP와 서버 내부 IP로 바꿉니다. 서버 자체가 공인 IP를 갖고 있으면 해당 환경에 맞춰 external-ip 필요 여부를 확인합니다.

6.2 브라우저와 Python 서버에 같은 TURN 정보 전달

.env의 ICE_SERVERS_JSON 한 줄을 수정합니다.

dotenv
ICE_SERVERS_JSON=[{"urls":"stun:meet.example.com:3478"},{"urls":"turn:meet.example.com:3478?transport=udp","username":"meeting","credential":"생성한_영문숫자_비밀번호"}]

도메인·사용자·비밀번호는 turnserver.conf와 일치해야 합니다. JSON 따옴표를 유지하고 여러 줄로 나누지 않습니다. DNS를 CDN 웹 프록시에 연결했다면 웹 HTTPS는 열려도 3478이나 미디어 UDP는 프록시되지 않을 수 있으므로 TURN 주소가 실제 coturn 서버로 도달하도록 구성합니다.

이 예제 coturn은 TLS를 끈 3478 기반 구성입니다. UDP를 차단하는 조직망에서 항상 동작한다고 보장하지 않습니다. 해당 조직망이 허용하는 TURN 전송 방식과 별도 TLS TURN 배포가 필요한지 네트워크 관리자와 확인하세요.

TURN 계정은 회의 참석자에게 연결 설정으로 전달됩니다. 현재의 고정 계정 구성은 소규모 시험용이며, 외부 공개 운영에는 임시 자격 증명 등 운영 보강이 필요합니다. 예제의 REPLACE_WITH_LONG_RANDOM_PASSWORD를 그대로 사용하지 않습니다.

7 서버 빌드와 실행

7.1 설정 문법 확인

bash
cd /opt/moa
sudo docker compose -p moa config --quiet

명령이 종료 코드 0으로 끝나면 Compose 문법과 필요한 변수 해석이 통과한 것입니다. 이것만으로 네트워크 설정이 검증되는 것은 아닙니다. .env의 비밀번호가 보이는 전체 config 출력을 공개하지 마세요.

7.2 사용할 구성 하나로 실행

TURN 없이 직접 연결 시험:

bash
sudo docker compose -p moa up -d --build

TURN도 함께 실행:

bash
sudo docker compose -p moa --profile turn up -d --build

-d는 터미널에서 분리해 실행하는 옵션입니다. SSH 창을 닫아도 서버가 유지됩니다. 최초에는 이미지 다운로드와 패키지 설치 시간이 필요합니다. 기본 웹 서비스는 meeting, https이고 TURN 프로필 사용 시 turn이 추가됩니다.

7.3 실행 결과 확인

bash
sudo docker compose -p moa --profile turn ps -a
curl -fsS http://127.0.0.1:8000/api/health
curl -fsS http://127.0.0.1:8000/api/config
sudo docker compose -p moa logs --tail=100 meeting https

정상 확인 기준:

  • meeting이 실행 중이고 잠시 후 healthy가 됩니다.
  • /api/health에서 {"ok":true}가 나옵니다.
  • 모델을 설치했다면 /api/config의 speech_available이 true입니다.
  • 도메인으로 브라우저를 열면 인증서 오류 없이 접속 설정 화면이 보입니다.
  • 서버 주소 연결 확인이 성공합니다.

TURN 로그는 sudo docker compose -p moa --profile turn logs --tail=100 turn으로 확인합니다. logs -f로 따라보기 중 Ctrl+C는 로그 보기만 끝내며, -d로 실행한 서버는 중지하지 않습니다.

8 설치 후 실제 회의 시험

  1. 서로 다른 PC 두 대에서 HTTPS 주소를 엽니다.
  2. 한 PC에서 회의 모드 방을 만들고 다른 PC에 접속 ID를 공유합니다.
  3. 양쪽 스피커와 카메라를 켜고 영상을 확인합니다.
  4. 방장을 발표자로 두고 마이크를 켜 음성을 확인합니다.
  5. 다른 사람에게 발표권을 넘기고 반대 방향 음성을 확인합니다.
  6. 발표권이 없는 사람의 음성이 전달되지 않는지 확인합니다.
  7. 자동 회의록을 켜고 한국어 문장을 말한 뒤 전사 내용을 확인합니다.
  8. 발표자의 문서 창을 공유하고 다른 PC에서 발표자 화면을 봅니다.
  9. 화이트보드 그림이 다른 PC에 표시되는지 확인합니다.
  10. 회의록을 저장하고 한글 내용을 확인합니다.
  11. 인터넷 사용 환경이면 한 PC를 다른 인터넷 회선으로 옮겨 같은 시험을 반복합니다.
  12. 자동 시작 안내에 따라 재부팅 후 확인합니다.

설정된 최대 인원으로도 시험하고 sudo docker stats --no-stream으로 CPU·메모리·네트워크 사용량을 확인합니다. 장치 인식 품질과 외부 네트워크 성능은 실제 환경에서 검증해야 합니다.

10.2 실행 중 일관된 SQLite 사본 만들기

bash
cd /opt/moa
mkdir -p backups
sudo docker compose -p moa exec -T meeting python - <<'PY'
import sqlite3
source = sqlite3.connect('/app/data/meetings.db')
target = sqlite3.connect('/app/data/backup-latest.db')
try:
    source.backup(target)
finally:
    target.close()
    source.close()
print('SQLite snapshot ready')
PY
MEETING_BACKUP="./backups/meetings-$(date +%Y%m%d-%H%M%S).db"
sudo docker compose -p moa cp meeting:/app/data/backup-latest.db "$MEETING_BACKUP"
sudo chmod 600 "$MEETING_BACKUP"

backup-latest.db는 다음 백업 때 갱신되는 임시 스냅샷입니다. 날짜가 붙은 파일을 별도 저장소에도 보관하세요. 백업에는 회의 텍스트가 있으므로 관리자만 읽도록 합니다. 전사 중 아직 DB에 반영되지 않은 발언은 그 시점 스냅샷에 포함되지 않습니다.

10.3 종료된 방의 회의록 내보내기

Docker 이미지에는 scripts/를 복사하지 않으므로 아래는 호스트의 Python 3.8 이상에서 백업 사본을 읽습니다. 데이터 클래스와 기본 SQLite 모듈만 필요합니다.

bash

--list에서 확인한 긴 내부 id를 ROOM_ID 자리에 넣습니다. 이는 참석자 초대에 쓰는 12자리 방 접속 ID와 다릅니다. 파일명도 실제 백업 이름으로 바꿔야 합니다. 결과 Markdown을 안전한 방식으로 방장에게 전달하세요.

10.4 백업 복원 원칙

복원은 기존 기록을 덮어쓸 수 있으므로 회의가 없는 시간에 진행합니다. 먼저 현재 DB를 위 방법으로 별도 백업하고 meeting 서비스를 중지합니다. 선택한 스냅샷의 무결성을 sqlite3의 PRAGMA integrity_check로 확인한 뒤, moa_meeting-data 볼륨에 SQLite 백업 API로 복원합니다. 컨테이너 사용자의 UID/GID는 10001이며 DB 쓰기 권한을 유지해야 합니다.

서버를 다시 시작한 뒤 /api/health, /api/config, 관리자 내보내기로 기록을 확인합니다. DB를 복원해도 진행 중이던 방이나 화이트보드가 돌아오지는 않습니다. 실제 운영 전에는 별도 시험 볼륨에서 복원 리허설을 수행하세요.

Windows 시작프로그램 폴더는 로그인 후 실행하는 방법입니다. 전원만 켜도 실행돼야 하는 서버는 작업 스케줄러의 시스템 시작 시 방식을 사용하세요. Microsoft는 부팅 트리거와 로그온 트리거를 구분합니다. Windows 작업 스케줄 유형.

자동으로 서버가 다시 실행되는 것과 이전 회의가 복구되는 것은 다릅니다. 재부팅 후에는 새 방을 만들어 새 접속 ID를 배포해야 합니다. 이전 회의록 텍스트는 DB에서 관리자가 내보낼 수 있습니다.

2 Ubuntu Docker 자동 시작 등록

2.1 Docker 서비스 등록

Ubuntu에서 실행합니다.

bash
sudo systemctl enable --now docker.service
sudo systemctl enable --now containerd.service
systemctl is-enabled docker.service
systemctl is-active docker.service

정상 결과는 enabled, active입니다. enable은 부팅 시 시작 등록이고 --now는 지금도 시작한다는 뜻입니다. 서비스가 실패하면 sudo journalctl -u docker.service -n 100 --no-pager로 확인합니다. Docker Linux 자동 시작 안내.

2.2 애플리케이션 컨테이너 등록

현재 compose.yaml의 meeting, https, turn에는 모두 다음 정책이 들어 있습니다.

yaml
restart: unless-stopped

서비스를 한 번 생성·실행합니다.

bash
cd /opt/moa
# TURN 없는 환경
sudo docker compose -p moa up -d --build
# TURN까지 설정한 환경은 위 명령 대신 다음 사용
sudo docker compose -p moa --profile turn up -d --build

이후 Docker가 부팅 때 시작하면 생성된 컨테이너도 정책에 따라 다시 실행됩니다. 별도의 시작프로그램 폴더나 cron @reboot, 컨테이너를 재실행하는 추가 systemd 서비스를 등록할 필요가 없습니다.

unless-stopped는 관리자가 수동으로 중지한 컨테이너를 재부팅 뒤에도 자동으로 되살리지 않는 정책입니다. stop한 서비스는 다시 up -d 또는 start로 재개해야 합니다. down으로 컨테이너를 제거했다면 부팅만으로 다시 만들어지지 않습니다. Docker 재시작 정책.

2.3 등록 상태 확인

bash
cd /opt/moa
sudo docker compose -p moa --profile turn ps -a
MEETING_CID=$(sudo docker compose -p moa ps -q meeting)
sudo docker inspect --format '{{.HostConfig.RestartPolicy.Name}}' "$MEETING_CID"
curl -fsS http://127.0.0.1:8000/api/health

정책 출력은 unless-stopped, 상태 확인 응답은 {"ok":true}여야 합니다. MEETING_CID가 비어 있으면 컨테이너가 생성되어 있는지, 프로젝트 이름이 맞는지부터 확인하세요.

healthy 상태는 앱의 HTTP 응답을 확인하는 것입니다. 미디어 UDP, TURN 인증, 실제 마이크와 음성 인식 품질까지 보증하는 상태는 아닙니다. 또한 healthcheck 실패만으로 자동 재시작되지는 않으며 프로세스 종료에 대한 재시작 정책과 구분합니다.

2.4 실제 재부팅 시험

  1. 회의가 진행 중이지 않은 시간을 정합니다.
  2. 진행 중인 회의록과 필요한 화이트보드 화면을 저장합니다.
  3. 서버가 실행 중인 상태에서 다음 명령을 실행합니다.
bash
sudo reboot

SSH 연결이 끊기는 것은 정상입니다. 서버 부팅 뒤 다시 접속하여 다음을 확인합니다.

bash
systemctl is-active docker.service
cd /opt/moa
sudo docker compose -p moa --profile turn ps -a
curl -fsS http://127.0.0.1:8000/api/health
curl -fsS http://127.0.0.1:8000/api/config
  1. 관리자가 docker compose up을 수동으로 실행하지 않아도 컨테이너가 올라왔는지 확인합니다.
  2. 외부 PC에서 HTTPS 주소를 열고 새 방 생성·입장을 시험합니다.
  3. 모델 상태와 실제 영상·음성까지 확인합니다.

Caddy나 TURN이 Python보다 먼저 시작할 수 있으므로 부팅 직후 잠깐의 연결 실패만으로 고장으로 판단하지 않습니다. 서비스 상태와 로그를 보면서 준비 완료를 확인합니다.

2.5 수동 중지 이후에도 다음 부팅에 시작시키고 싶은 경우

현재 동작을 먼저 이해하고 필요할 때만 정책을 변경합니다. compose.yaml의 각 서비스에서 restart: unless-stopped를 restart: always로 바꾸고 다음으로 반영합니다.

bash
cd /opt/moa
sudo docker compose -p moa --profile turn up -d

always는 수동 중지 직후 계속 재실행하는 의미가 아니라 Docker 데몬 재시작 시 다시 시작하는 동작에 차이가 있습니다. 프로젝트 파일의 기본값은 unless-stopped이며 이 문서 작성으로 자동 변경하지 않았습니다.

3 Ubuntu 자동 시작 해제와 재개

3.1 이 화상회의만 잠시 중지

bash
cd /opt/moa
sudo docker compose -p moa --profile turn stop

기본 정책에서는 재부팅 뒤에도 중지 상태를 유지합니다. 재개하려면:

bash
sudo docker compose -p moa --profile turn up -d

3.2 이 화상회의 컨테이너를 정리

bash
sudo docker compose -p moa --profile turn down

컨테이너를 제거하지만 기본적으로 이름 있는 데이터 볼륨은 남습니다. 삭제 후에는 up -d로 다시 생성해야 합니다. 기록까지 지우는 옵션은 일반 중지에 사용하지 않습니다.

3.3 Docker 전체 자동 시작 해제

Docker 전체를 끄면 다른 애플리케이션도 영향을 받습니다. 다른 서비스가 있는 서버에서는 위의 화상회의 컨테이너 중지만 사용하세요. Docker 전체를 의도적으로 관리해야 할 때만 시스템 관리자가 Docker·소켓·containerd 서비스의 자동 시작 설정을 함께 점검합니다.

4 Linux에서 Python을 직접 실행하는 경우의 systemd

이 절은 Docker를 쓰지 않고 별도로 Python 3.12와 프로젝트 가상환경을 준비한 서버에만 적용합니다. Ubuntu 20.04 기본 Python 3.8을 그대로 쓰는 절차가 아닙니다. Python 설치 경로와 패키지 공급은 해당 서버의 운영 기준을 따릅니다.

4.1 가상환경과 실행 계정

/opt/moa에 코드가 있고 python3.12가 설치된 상태에서:

bash
cd /opt/moa
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python scripts/download_model.py
id moa

moa 계정이 없다면 새 서비스 계정을 만듭니다.

bash
sudo useradd --system --home-dir /opt/moa --shell /usr/sbin/nologin moa
sudo install -d -o moa -g moa -m 0750 /var/lib/moa
sudo touch /etc/moa.env
sudo chown root:moa /etc/moa.env
sudo chmod 640 /etc/moa.env
sudo nano /etc/moa.env

/etc/moa.env에는 Docker용 /app 경로 대신 실제 호스트 경로를 씁니다.

dotenv
DB_PATH=/var/lib/moa/meetings.db
VOSK_MODEL_PATH=/opt/moa/models/vosk-model-small-ko-0.22
MAX_PARTICIPANTS=8
MAX_ROOMS=30
ALLOWED_ORIGINS=
ICE_SERVERS_JSON=[]

코드·가상환경·모델은 moa 계정이 읽고 실행할 수 있어야 하고, /var/lib/moa에는 쓸 수 있어야 합니다. 관리자 전용 홈 디렉토리의 Python을 참조하는 가상환경은 서비스 계정에서 실행되지 않을 수 있습니다. 시스템에서 접근 가능한 Python으로 가상환경을 만드세요.

4.2 서비스 파일 작성

bash
sudo nano /etc/systemd/system/moa-relay.service

내용:

ini
[Unit]
Description=Moa Python Meeting Relay
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
User=moa
Group=moa
WorkingDirectory=/opt/moa
ExecStart=/opt/moa/.venv/bin/python /opt/moa/server.py --host 127.0.0.1 --port 8000 --env-file /etc/moa.env
Environment=PYTHONUNBUFFERED=1
Restart=on-failure
RestartSec=5
TimeoutStopSec=30
UMask=0027
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target

Docker의 meeting 컨테이너와 이 서비스를 같은 포트에서 동시에 실행하면 안 됩니다. 직접 실행 방식에서도 HTTPS 프록시와 필요시 coturn은 별도 서비스를 구성해야 하며, 위 unit은 Python 중계 서버만 시작합니다.

4.3 등록과 관리

bash
sudo systemctl daemon-reload
sudo systemctl enable --now moa-relay.service
sudo systemctl status moa-relay.service --no-pager
sudo journalctl -u moa-relay.service -n 100 --no-pager
curl -fsS http://127.0.0.1:8000/api/health

재시작은 sudo systemctl restart moa-relay.service, 자동 시작 해제와 즉시 중지는 sudo systemctl disable --now moa-relay.service입니다. 로그는 journalctl -u moa-relay.service -f로 따라볼 수 있습니다. 진행 중 서버를 재시작하면 방이 종료됩니다.

5 Windows 부팅 자동 시작

Windows는 개발·시험용으로 설명합니다. 다른 PC 사용자를 받는 운영 서버는 HTTPS와 네트워크 구성이 추가로 필요합니다.

5.1 등록할 실행 파일과 경로 확인

현재 PC에서:

항목값
작업 이름 예MoaMeetingRelay
프로그램C:\Users\063\Downloads\교육_1014\화상회의\.venv\Scripts\python.exe
인수"C:\Users\063\Downloads\교육_1014\화상회의\RelayServer\server.py" --host 127.0.0.1 --port 8000
시작 위치C:\Users\063\Downloads\교육_1014\화상회의\중계서버

새 PC에서 RelayServer/.venv를 만들었다면 프로그램 경로도 그 위치로 변경합니다. 가상환경이 참조하는 원본 Python도 작업 실행 계정이 읽고 실행할 수 있어야 합니다. Python, 프로젝트 폴더, 모델을 나중에 이동하면 작업 설정도 다시 맞춰야 합니다.

5.2 작업 스케줄러에서 등록

  1. 시작 메뉴에서 작업 스케줄러를 검색해 엽니다. 부팅 작업 등록에는 관리자 권한이 필요할 수 있습니다.
  2. 오른쪽에서 작업 만들기를 선택합니다.
  3. 일반 탭에서 이름을 MoaMeetingRelay로 입력합니다.
  4. 실행 계정은 프로젝트·Python·모델을 읽고 data 폴더에 쓸 수 있는 계정으로 선택합니다.
  5. 사용자의 로그온 여부에 관계없이 실행을 선택합니다. 서버 실행 자체에 관리자 권한이 꼭 필요한 것은 아니므로 불필요하게 SYSTEM이나 최고 권한을 사용하지 않습니다.
  6. 트리거 탭에서 새로 만들기 → 작업 시작: 시작할 때/시스템 시작 시를 선택합니다. 네트워크 준비를 위해 30초 정도 지연을 설정할 수 있습니다.
  7. 동작 탭에서 프로그램 시작을 선택하고 위 표의 프로그램·인수·시작 위치를 각각 입력합니다. 전체 명령을 프로그램 칸 하나에 넣지 않습니다.
  8. 조건 탭에서 서버용 전원 정책에 맞춰 유휴·전원 조건을 확인합니다. 노트북을 실제로 배터리에서도 운영할 경우에만 AC 전원 조건을 조정합니다.
  9. 설정 탭에서 요청 시 작업 실행 허용을 켭니다.
  10. 실패 시 다시 시작은 예를 들어 1분 간격·3회로 설정합니다.
  11. 작업이 다음 시간 이상 실행되면 중지 같은 장시간 실행 제한을 해제합니다. 서버는 계속 실행되는 프로그램입니다.
  12. 이미 실행 중일 때는 새 인스턴스 시작 안 함을 선택해 중복 서버를 막습니다.
  13. 저장하고 요청되는 실행 계정 인증을 완료합니다. 인증 정보는 작업 스케줄러에 입력하며 문서나 명령 파일에 비밀번호를 적지 않습니다.

부팅 트리거는 시스템 시작 시 작업을 실행하도록 구성하는 방식입니다. 계정과 권한 조건도 충족되어야 합니다. Microsoft 부팅 트리거 예제.

5.3 수동 시험 후 재부팅 시험

  1. 콘솔에서 수동 실행한 서버가 있으면 먼저 그 콘솔에서 Ctrl+C로 종료합니다.
  2. 작업 스케줄러에서 MoaMeetingRelay를 선택하고 실행을 누릅니다.
  3. 상태가 실행 중인지 확인합니다. 계속 실행되는 서버에서는 작업 완료가 아니라 실행 중 상태가 정상입니다.
  4. 브라우저에서 http://localhost:8000을 엽니다.
  5. 필요하면 PowerShell에서 다음을 확인합니다.
powershell
Invoke-RestMethod http://127.0.0.1:8000/api/health
Invoke-RestMethod http://127.0.0.1:8000/api/config
Get-ScheduledTask -TaskName MoaMeetingRelay
Get-ScheduledTaskInfo -TaskName MoaMeetingRelay
  1. 회의가 없는 시간에 PC를 재부팅합니다.
  2. 별도 수동 실행 없이 작업이 시작되는지 확인합니다. 로그인 전 시험이 필요하다면 적절한 HTTPS·방화벽 구성을 갖춘 다른 PC에서 확인합니다. 기본 127.0.0.1 바인딩은 다른 PC에서 접근할 수 없습니다.
  3. 모델 준비와 실제 새 방 생성도 확인합니다.

화면에 콘솔이 없다고 실행되지 않은 것은 아닙니다. 비대화형 작업은 창을 표시하지 않을 수 있습니다. 반대로 부팅에 성공했어도 Windows가 절전 상태로 들어가면 네트워크 서비스가 계속 제공되지 않으므로 서버 운영에 맞는 절전 설정을 적용합니다.

5.4 작업 중지와 해제

작업 스케줄러에서 해당 작업의 끝내기로 현재 서버를 중지하고, 사용 안 함으로 다음 부팅 실행을 막습니다. 삭제는 등록 자체를 제거합니다. 완료 후 포트와 health 응답을 확인하세요. 실행 계정 비밀번호나 폴더 경로가 바뀌면 작업 설정도 갱신해야 합니다.

5.5 시작프로그램 폴더를 사용하는 간단한 대안

로그인할 때만 실행돼도 되는 개발 PC라면 Win+R에 shell:startup을 입력하고 RelayServer/run.cmd의 바로가기를 넣을 수 있습니다. Python 실행 파일 자체를 복사하지 않습니다. 해제하려면 이 바로가기를 제거합니다.

이 방식은 로그인 전에는 시작하지 않고 실패 시 자동 복구도 제공하지 않습니다. 작업 스케줄러와 동시에 등록하면 포트 중복이 생길 수 있으므로 둘 중 하나만 사용합니다.
