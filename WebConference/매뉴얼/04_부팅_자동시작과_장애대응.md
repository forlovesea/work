# 부팅 자동 시작과 장애 대응

서버 재부팅 뒤 사람이 로그인하거나 터미널에서 명령을 입력하지 않아도 중계 서버가 시작되도록 구성하는 방법입니다. Ubuntu Docker 방식이 기본이고, 직접 Python을 운영하는 Linux와 Windows 방식은 별도 대안입니다. 같은 서버를 두 방법으로 중복 실행하지 않습니다.

## 1 자동 시작 방식 선택

| 설치 방식 | 자동 시작 방법 | 로그인 필요 |
| --- | --- | --- |
| Ubuntu Docker | Docker 서비스 자동 시작 + Compose 재시작 정책 | 불필요 |
| Linux Python 직접 실행 | systemd 서비스 | 불필요 |
| Windows Python 직접 실행 | 작업 스케줄러의 시스템 시작 트리거 | 설정에 따라 불필요 |
| Windows 시작프로그램 폴더 | 로그인 시 바로가기 실행 | 필요 |

Windows 시작프로그램 폴더는 로그인 후 실행하는 방법입니다. 전원만 켜도 실행돼야 하는 서버는 작업 스케줄러의 **시스템 시작 시** 방식을 사용하세요. Microsoft는 부팅 트리거와 로그온 트리거를 구분합니다. [Windows 작업 스케줄 유형](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create).

자동으로 서버가 다시 실행되는 것과 이전 회의가 복구되는 것은 다릅니다. 재부팅 후에는 **새 방을 만들어 새 접속 ID를 배포**해야 합니다. 이전 회의록 텍스트는 DB에서 관리자가 내보낼 수 있습니다.

## 2 Ubuntu Docker 자동 시작 등록

### 2.1 Docker 서비스 등록

Ubuntu에서 실행합니다.

```bash
sudo systemctl enable --now docker.service
sudo systemctl enable --now containerd.service
systemctl is-enabled docker.service
systemctl is-active docker.service
```

정상 결과는 `enabled`, `active`입니다. `enable`은 부팅 시 시작 등록이고 `--now`는 지금도 시작한다는 뜻입니다. 서비스가 실패하면 `sudo journalctl -u docker.service -n 100 --no-pager`로 확인합니다. [Docker Linux 자동 시작 안내](https://docs.docker.com/engine/install/linux-postinstall/).

### 2.2 애플리케이션 컨테이너 등록

현재 `compose.yaml`의 `meeting`, `https`, `turn`에는 모두 다음 정책이 들어 있습니다.

```yaml
restart: unless-stopped
```

서비스를 한 번 생성·실행합니다.

```bash
cd /opt/moa
# TURN 없는 환경
sudo docker compose -p moa up -d --build
# TURN까지 설정한 환경은 위 명령 대신 다음 사용
sudo docker compose -p moa --profile turn up -d --build
```

이후 Docker가 부팅 때 시작하면 생성된 컨테이너도 정책에 따라 다시 실행됩니다. 별도의 시작프로그램 폴더나 `cron @reboot`, 컨테이너를 재실행하는 추가 systemd 서비스를 등록할 필요가 없습니다.

`unless-stopped`는 관리자가 수동으로 중지한 컨테이너를 재부팅 뒤에도 자동으로 되살리지 않는 정책입니다. `stop`한 서비스는 다시 `up -d` 또는 `start`로 재개해야 합니다. `down`으로 컨테이너를 제거했다면 부팅만으로 다시 만들어지지 않습니다. [Docker 재시작 정책](https://docs.docker.com/engine/containers/start-containers-automatically/).

### 2.3 등록 상태 확인

```bash
cd /opt/moa
sudo docker compose -p moa --profile turn ps -a
MEETING_CID=$(sudo docker compose -p moa ps -q meeting)
sudo docker inspect --format '{{.HostConfig.RestartPolicy.Name}}' "$MEETING_CID"
curl -fsS http://127.0.0.1:8000/api/health
```

정책 출력은 `unless-stopped`, 상태 확인 응답은 `{"ok":true}`여야 합니다. `MEETING_CID`가 비어 있으면 컨테이너가 생성되어 있는지, 프로젝트 이름이 맞는지부터 확인하세요.

`healthy` 상태는 앱의 HTTP 응답을 확인하는 것입니다. 미디어 UDP, TURN 인증, 실제 마이크와 음성 인식 품질까지 보증하는 상태는 아닙니다. 또한 healthcheck 실패만으로 자동 재시작되지는 않으며 프로세스 종료에 대한 재시작 정책과 구분합니다.

### 2.4 실제 재부팅 시험

1. 회의가 진행 중이지 않은 시간을 정합니다.
2. 진행 중인 회의록과 필요한 화이트보드 화면을 저장합니다.
3. 서버가 실행 중인 상태에서 다음 명령을 실행합니다.

```bash
sudo reboot
```

SSH 연결이 끊기는 것은 정상입니다. 서버 부팅 뒤 다시 접속하여 다음을 확인합니다.

```bash
systemctl is-active docker.service
cd /opt/moa
sudo docker compose -p moa --profile turn ps -a
curl -fsS http://127.0.0.1:8000/api/health
curl -fsS http://127.0.0.1:8000/api/config
```

4. 관리자가 `docker compose up`을 수동으로 실행하지 않아도 컨테이너가 올라왔는지 확인합니다.
5. 외부 PC에서 HTTPS 주소를 열고 새 방 생성·입장을 시험합니다.
6. 모델 상태와 실제 영상·음성까지 확인합니다.

Caddy나 TURN이 Python보다 먼저 시작할 수 있으므로 부팅 직후 잠깐의 연결 실패만으로 고장으로 판단하지 않습니다. 서비스 상태와 로그를 보면서 준비 완료를 확인합니다.

### 2.5 수동 중지 이후에도 다음 부팅에 시작시키고 싶은 경우

현재 동작을 먼저 이해하고 필요할 때만 정책을 변경합니다. `compose.yaml`의 각 서비스에서 `restart: unless-stopped`를 `restart: always`로 바꾸고 다음으로 반영합니다.

```bash
cd /opt/moa
sudo docker compose -p moa --profile turn up -d
```

`always`는 수동 중지 직후 계속 재실행하는 의미가 아니라 Docker 데몬 재시작 시 다시 시작하는 동작에 차이가 있습니다. 프로젝트 파일의 기본값은 `unless-stopped`이며 이 문서 작성으로 자동 변경하지 않았습니다.

## 3 Ubuntu 자동 시작 해제와 재개

### 3.1 이 화상회의만 잠시 중지

```bash
cd /opt/moa
sudo docker compose -p moa --profile turn stop
```

기본 정책에서는 재부팅 뒤에도 중지 상태를 유지합니다. 재개하려면:

```bash
sudo docker compose -p moa --profile turn up -d
```

### 3.2 이 화상회의 컨테이너를 정리

```bash
sudo docker compose -p moa --profile turn down
```

컨테이너를 제거하지만 기본적으로 이름 있는 데이터 볼륨은 남습니다. 삭제 후에는 `up -d`로 다시 생성해야 합니다. 기록까지 지우는 옵션은 일반 중지에 사용하지 않습니다.

### 3.3 Docker 전체 자동 시작 해제

Docker 전체를 끄면 다른 애플리케이션도 영향을 받습니다. 다른 서비스가 있는 서버에서는 위의 화상회의 컨테이너 중지만 사용하세요. Docker 전체를 의도적으로 관리해야 할 때만 시스템 관리자가 Docker·소켓·containerd 서비스의 자동 시작 설정을 함께 점검합니다.

## 4 Linux에서 Python을 직접 실행하는 경우의 systemd

이 절은 Docker를 쓰지 않고 **별도로 Python 3.12와 프로젝트 가상환경을 준비한 서버**에만 적용합니다. Ubuntu 20.04 기본 Python 3.8을 그대로 쓰는 절차가 아닙니다. Python 설치 경로와 패키지 공급은 해당 서버의 운영 기준을 따릅니다.

### 4.1 가상환경과 실행 계정

`/opt/moa`에 코드가 있고 `python3.12`가 설치된 상태에서:

```bash
cd /opt/moa
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python scripts/download_model.py
id moa
```

`moa` 계정이 없다면 새 서비스 계정을 만듭니다.

```bash
sudo useradd --system --home-dir /opt/moa --shell /usr/sbin/nologin moa
sudo install -d -o moa -g moa -m 0750 /var/lib/moa
sudo touch /etc/moa.env
sudo chown root:moa /etc/moa.env
sudo chmod 640 /etc/moa.env
sudo nano /etc/moa.env
```

`/etc/moa.env`에는 Docker용 `/app` 경로 대신 실제 호스트 경로를 씁니다.

```dotenv
DB_PATH=/var/lib/moa/meetings.db
VOSK_MODEL_PATH=/opt/moa/models/vosk-model-small-ko-0.22
MAX_PARTICIPANTS=8
MAX_ROOMS=30
ALLOWED_ORIGINS=
ICE_SERVERS_JSON=[]
```

코드·가상환경·모델은 `moa` 계정이 읽고 실행할 수 있어야 하고, `/var/lib/moa`에는 쓸 수 있어야 합니다. 관리자 전용 홈 디렉토리의 Python을 참조하는 가상환경은 서비스 계정에서 실행되지 않을 수 있습니다. 시스템에서 접근 가능한 Python으로 가상환경을 만드세요.

### 4.2 서비스 파일 작성

```bash
sudo nano /etc/systemd/system/moa-relay.service
```

내용:

```ini
[Unit]
Description=Moa Python Meeting Relay
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
User=moa
Group=moa
WorkingDirectory=/opt/moa
ExecStart=/opt/moa/.venv/bin/python /opt/moa/server.py --host 127.0.0.1 --port 8000 --env-file /etc/moa.env
Environment=PYTHONUNBUFFERED=1
Restart=on-failure
RestartSec=5
TimeoutStopSec=30
UMask=0027
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

Docker의 `meeting` 컨테이너와 이 서비스를 같은 포트에서 동시에 실행하면 안 됩니다. 직접 실행 방식에서도 HTTPS 프록시와 필요시 coturn은 별도 서비스를 구성해야 하며, 위 unit은 Python 중계 서버만 시작합니다.

### 4.3 등록과 관리

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now moa-relay.service
sudo systemctl status moa-relay.service --no-pager
sudo journalctl -u moa-relay.service -n 100 --no-pager
curl -fsS http://127.0.0.1:8000/api/health
```

재시작은 `sudo systemctl restart moa-relay.service`, 자동 시작 해제와 즉시 중지는 `sudo systemctl disable --now moa-relay.service`입니다. 로그는 `journalctl -u moa-relay.service -f`로 따라볼 수 있습니다. 진행 중 서버를 재시작하면 방이 종료됩니다.

## 5 Windows 부팅 자동 시작

Windows는 개발·시험용으로 설명합니다. 다른 PC 사용자를 받는 운영 서버는 HTTPS와 네트워크 구성이 추가로 필요합니다.

### 5.1 등록할 실행 파일과 경로 확인

현재 PC에서:

| 항목 | 값 |
| --- | --- |
| 작업 이름 예 | `MoaMeetingRelay` |
| 프로그램 | `C:\Users\063\Downloads\교육_1014\화상회의\.venv\Scripts\python.exe` |
| 인수 | `"C:\Users\063\Downloads\교육_1014\화상회의\RelayServer\server.py" --host 127.0.0.1 --port 8000` |
| 시작 위치 | `C:\Users\063\Downloads\교육_1014\화상회의\중계서버` |

새 PC에서 `RelayServer/.venv`를 만들었다면 프로그램 경로도 그 위치로 변경합니다. 가상환경이 참조하는 원본 Python도 작업 실행 계정이 읽고 실행할 수 있어야 합니다. Python, 프로젝트 폴더, 모델을 나중에 이동하면 작업 설정도 다시 맞춰야 합니다.

### 5.2 작업 스케줄러에서 등록

1. 시작 메뉴에서 **작업 스케줄러**를 검색해 엽니다. 부팅 작업 등록에는 관리자 권한이 필요할 수 있습니다.
2. 오른쪽에서 **작업 만들기**를 선택합니다.
3. 일반 탭에서 이름을 `MoaMeetingRelay`로 입력합니다.
4. 실행 계정은 프로젝트·Python·모델을 읽고 `data` 폴더에 쓸 수 있는 계정으로 선택합니다.
5. **사용자의 로그온 여부에 관계없이 실행**을 선택합니다. 서버 실행 자체에 관리자 권한이 꼭 필요한 것은 아니므로 불필요하게 SYSTEM이나 최고 권한을 사용하지 않습니다.
6. 트리거 탭에서 **새로 만들기 → 작업 시작: 시작할 때/시스템 시작 시**를 선택합니다. 네트워크 준비를 위해 30초 정도 지연을 설정할 수 있습니다.
7. 동작 탭에서 **프로그램 시작**을 선택하고 위 표의 프로그램·인수·시작 위치를 각각 입력합니다. 전체 명령을 프로그램 칸 하나에 넣지 않습니다.
8. 조건 탭에서 서버용 전원 정책에 맞춰 유휴·전원 조건을 확인합니다. 노트북을 실제로 배터리에서도 운영할 경우에만 AC 전원 조건을 조정합니다.
9. 설정 탭에서 **요청 시 작업 실행 허용**을 켭니다.
10. 실패 시 다시 시작은 예를 들어 1분 간격·3회로 설정합니다.
11. **작업이 다음 시간 이상 실행되면 중지** 같은 장시간 실행 제한을 해제합니다. 서버는 계속 실행되는 프로그램입니다.
12. 이미 실행 중일 때는 **새 인스턴스 시작 안 함**을 선택해 중복 서버를 막습니다.
13. 저장하고 요청되는 실행 계정 인증을 완료합니다. 인증 정보는 작업 스케줄러에 입력하며 문서나 명령 파일에 비밀번호를 적지 않습니다.

부팅 트리거는 시스템 시작 시 작업을 실행하도록 구성하는 방식입니다. 계정과 권한 조건도 충족되어야 합니다. [Microsoft 부팅 트리거 예제](https://learn.microsoft.com/en-us/windows/win32/taskschd/boot-trigger-example--scripting-).

### 5.3 수동 시험 후 재부팅 시험

1. 콘솔에서 수동 실행한 서버가 있으면 먼저 그 콘솔에서 `Ctrl+C`로 종료합니다.
2. 작업 스케줄러에서 `MoaMeetingRelay`를 선택하고 **실행**을 누릅니다.
3. 상태가 실행 중인지 확인합니다. 계속 실행되는 서버에서는 작업 완료가 아니라 실행 중 상태가 정상입니다.
4. 브라우저에서 `http://localhost:8000`을 엽니다.
5. 필요하면 PowerShell에서 다음을 확인합니다.

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/health
Invoke-RestMethod http://127.0.0.1:8000/api/config
Get-ScheduledTask -TaskName MoaMeetingRelay
Get-ScheduledTaskInfo -TaskName MoaMeetingRelay
```

6. 회의가 없는 시간에 PC를 재부팅합니다.
7. 별도 수동 실행 없이 작업이 시작되는지 확인합니다. 로그인 전 시험이 필요하다면 적절한 HTTPS·방화벽 구성을 갖춘 다른 PC에서 확인합니다. 기본 127.0.0.1 바인딩은 다른 PC에서 접근할 수 없습니다.
8. 모델 준비와 실제 새 방 생성도 확인합니다.

화면에 콘솔이 없다고 실행되지 않은 것은 아닙니다. 비대화형 작업은 창을 표시하지 않을 수 있습니다. 반대로 부팅에 성공했어도 Windows가 절전 상태로 들어가면 네트워크 서비스가 계속 제공되지 않으므로 서버 운영에 맞는 절전 설정을 적용합니다.

### 5.4 작업 중지와 해제

작업 스케줄러에서 해당 작업의 **끝내기**로 현재 서버를 중지하고, **사용 안 함**으로 다음 부팅 실행을 막습니다. **삭제**는 등록 자체를 제거합니다. 완료 후 포트와 health 응답을 확인하세요. 실행 계정 비밀번호나 폴더 경로가 바뀌면 작업 설정도 갱신해야 합니다.

### 5.5 시작프로그램 폴더를 사용하는 간단한 대안

로그인할 때만 실행돼도 되는 개발 PC라면 `Win+R`에 `shell:startup`을 입력하고 `RelayServer/run.cmd`의 **바로가기**를 넣을 수 있습니다. Python 실행 파일 자체를 복사하지 않습니다. 해제하려면 이 바로가기를 제거합니다.

이 방식은 로그인 전에는 시작하지 않고 실패 시 자동 복구도 제공하지 않습니다. 작업 스케줄러와 동시에 등록하면 포트 중복이 생길 수 있으므로 둘 중 하나만 사용합니다.

## 6 서버 장애 대응표

| 증상 | 점검 | 조치 |
| --- | --- | --- |
| 부팅 후 전체 서비스 미실행 | `systemctl is-active docker`, 컨테이너 존재 여부 | Docker 활성화, 올바른 프로젝트로 `up -d` |
| 수동 stop 후 재부팅해도 안 올라옴 | `unless-stopped` 정책 | 의도한 동작. `up -d`로 재개 |
| `down` 후 부팅해도 안 올라옴 | 컨테이너 제거 여부 | `up -d`로 다시 생성 |
| `DOMAIN` 변수 오류 | `.env` 위치와 DOMAIN 값 | `/opt/moa/.env` 수정 후 config 확인 |
| 80/443 사용 중 | `sudo ss -lntp` | 기존 웹 서버와 포트 역할 조정 |
| 8000 사용 중 | 기존 수동 실행·systemd·Docker·예약 작업 | 의도한 방식 하나만 실행 |
| HTTPS 인증서 실패 | DNS, 잘못된 AAAA, 포트 전달, 80/443, 기존 프록시 | 도메인 도달 경로 수정 후 Caddy 로그 확인 |
| 화면은 열리나 영상이 안 나옴 | 미디어 UDP, ICE, TURN 계정, 공유기 NAT | 실제 외부 회선 시험 및 네트워크 설정 점검 |
| 음성이 안 들림 | 참여자 스피커, 발표권, 마이크, 브라우저 권한 | 먼저 참여자 설정 점검 후 네트워크 점검 |
| 음성 인식 옵션 비활성 | `/api/config`의 `speech_available`, 모델 파일 | 모델 설치·경로·읽기 권한 확인 후 회의 없는 시간에 재시작 |
| `readonly database` | 데이터 볼륨의 소유자·쓰기 권한 | Docker UID/GID 10001 또는 직접 서비스 계정의 권한 확인 |
| 방 접속 ID가 갑자기 무효 | 마지막 참석자 퇴장 또는 서버 재시작 | 새 방 생성. 이전 기록은 DB에서 내보내기 |
| 재배포 후 기록이 빈 것처럼 보임 | Compose 프로젝트 이름·DB 경로·볼륨 변경 | 기존 볼륨을 확인하고 추가 덮어쓰기 전에 백업 |
| 서버는 healthy인데 음성 인식 중단 | 애플리케이션의 인식 오류 로그 | 모델·CPU·메모리 점검. healthy는 HTTP 점검임 |
| 메모리·CPU 과다 | `docker stats`, 참석자·방 수 | 인원 제한, 영상 사용량, 서버 증설 검토 |
| Windows 예약 작업 즉시 종료 | 프로그램·인수·시작 위치·권한·포트 | 동일 실행 계정으로 직접 실행해 오류 확인 |
| Windows에서 한글 모델 경로 실패 | server.py 사용 여부와 모델 위치 | 제공된 진입점 사용. 이동한 경로와 권한 재확인 |
