# 공통 설계 초안

2026-09-29: 조회 API, Android 화면, 서버 알람 상태/이력, 사용자 확인 및 FCM 발송 큐를 구현했습니다. 아래 단계 목록은 초기 설계이며 현재 설정과 제약은 [알람·푸시 안내](alarms-and-push.md)를 따릅니다.

## 수집 클라이언트 구현 반영

TBC1000B V3.2.6 SNMP 프로그램을 기반으로 TCP/TLS 업로드를 구현했습니다. 전송 기본 주기는 5초이며 설정 UI에서 변경합니다. 서버 TCP/TLS 수신·인증·SQLite 저장·ACK·접속 이력·백업도 구현했습니다. 수집 wire 형식과 ACK는 [TCP 업로드 규격](tcp-upload-protocol.md)을 따릅니다. 아래 정규화 모델과 단계 목록은 초기 전체 시스템 설계이며 후속 API/알람/Android 구현 때 적용합니다.

## Android 알림 모델

Android는 일반 백그라운드 서비스와 데이터 동기화 foreground service에 실행 제약을 둡니다. 앱을 한 번 실행하면 프로세스가 영구적으로 살아 있는 방식은 보장하지 않습니다.

따라서 서버가 알람을 판정하고 사용자에게 보이는 긴급 알림에 FCM high priority를 사용합니다. 앱의 주기적 동기화는 보조 수단이며 즉시 안전 알람의 유일한 경로로 사용하지 않습니다. 알람 이력은 푸시 성공 여부와 독립적으로 서버에 남깁니다.

FCM은 별도 Google 서비스입니다. 자체 서버가 데이터를 저장하고 FCM으로 알림 전달을 요청합니다. Firebase 사용 가능 여부와 Android 기기의 Google Play 서비스 지원 여부를 확인해야 합니다.

푸시 전달은 즉시 도착이 보장되지 않습니다. 네트워크 단절, 알림 권한 거부, 강제 종료 등에 대한 상태 안내와 실제 기기 검증이 필요합니다. 무음/방해금지 모드에서도 소리가 반드시 난다고 약속하지 않습니다.

- https://developer.android.com/training/monitoring-device-state/doze-standby
- https://developer.android.com/develop/background-work/background-tasks
- https://firebase.google.com/docs/cloud-messaging/android-message-priority

## 공통 측정 규칙

- 스키마 버전은 schema_version으로 구분합니다.
- sample_id는 최초 수집 시 생성한 UUID이며 재전송에서도 유지합니다.
- 중복 키는 인증된 수집기 ID와 sample_id의 조합입니다. 중복 수신은 성공 응답하되 이력/알람을 추가 생성하지 않습니다.
- observed_at은 UTC ISO 8601 측정 시각입니다. 서버의 received_at은 서버에서 생성합니다.
- 재전송된 과거 데이터와 허용 범위를 벗어난 미래 시각은 최신 상태/실시간 알람 판정과 분리합니다.
- SOC/SOH 단위는 %, 전압은 V, 전류는 A, 온도는 섭씨입니다.
- modules 및 cells는 가변 길이이며 모듈/셀 번호 중복은 거부합니다.
- 수집 불가 값은 null입니다. null을 정상이나 0으로 해석하지 않습니다.
- quality는 good / partial / unavailable 중 하나입니다. 실제 값과 quality의 일관성도 검증합니다.
- 업로드 바디 크기, 배치 크기, 모듈/셀 개수 제한은 구현 시 명시합니다.

telemetry.example.json은 형식 예시이며 실제 장비 데이터나 안전 임계값이 아닙니다.

## 알람 생명주기

1. 서버가 현장/장비별 임계값, 지속시간, 히스테리시스로 알람 발생 여부를 판단합니다.
2. 같은 장비/모듈/셀/규칙의 활성 알람은 한 건으로 유지합니다.
3. 발생 및 복구 상태 전환을 기록하고 알림 발송 큐에 넣습니다.
4. 발송 실패는 재시도하며 event_id로 중복 표시를 줄입니다.
5. 사용자 확인은 별도 기록입니다. 확인했다고 장비의 위험 상태를 복구 처리하지 않습니다.

예정 규칙: 저 SOC, 고/저 셀 온도, 셀 과전압/저전압, 셀 편차, 장비 자체 고장 알람, 통신/업로드 중단. 수치는 장비 사양 확인 후 결정합니다.

## 구현 순서와 완료 조건

1. 환경 및 프로토콜 확정, 공통 데이터 스키마와 API 계약 작성.
2. 가상 수집기 → 서버 → DB → 조회 API 연결. 재전송 중복 및 순서 뒤바뀜 시험.
3. 서버 알람 판정, 복구, 통신 중단, 발송 큐 시험.
4. Android 설정·상태·이력·알림 화면과 FCM 연동.
5. 실제 장비 어댑터 및 실제 휴대폰 화면 꺼짐·네트워크 복구 시험.
6. 서버 운영 배포, 인증서, 백업/복구, 현장 수집기 자동 실행 구성.

초기 디렉터리 구성은 1단계의 설계 준비이며 각 단계 구현 완료를 뜻하지 않습니다.
